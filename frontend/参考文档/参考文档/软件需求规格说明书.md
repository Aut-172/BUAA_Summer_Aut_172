### 1.2 系统概述

生活助手平台是一款面向城市居民的综合本地生活服务Web应用，旨在整合外卖订餐、到店消费、休闲娱乐、生活服务等多种生活场景，连接用户与本地商家，实现“吃、喝、玩、乐、购”一键触达。系统主要功能包括：商家搜索与浏览、外卖点餐与订单追踪、到店团购与优惠核销、用户评价与评分、在线下单与支付、订单管理。

系统采用前后端分离架构，前端为基于Vue.js的单页面应用（SPA），后端采用Spring Boot + Spring Cloud微服务架构。平台注重商家信息的真实性、订单处理的及时性以及用户评价的客观性，致力于成为用户可信赖的本地生活指南。

- **用户**：普通消费者、合作商家、平台管理员
- **开发方**：5人学生开发团队（3人后端，2人前端）
- **支持机构**：无
- **运行现场**：团队自备服务器或云服务器（单机部署）

## 3 需求

### 3.1 所需的状态和方式

本系统为典型的Web应用，不涉及多种运行状态和方式的切换。系统运行时即为活动状态，用户通过浏览器访问。系统内部可能存在常规业务处理状态和系统维护状态（管理员操作），但不需特殊定义方式。

### 3.2 需求概述

#### 3.2.1 目标

- **开发意图**：为城市居民提供一站式本地生活服务平台，整合外卖、团购、评价等功能，解决用户需要在多个平台间切换的痛点；同时为本地商家提供线上获客和订单管理渠道。
- **应用目标**：消费者通过Web端完成从浏览、下单到支付的完整业务流程；商家通过Web后台管理商品、处理订单；管理员通过后台审核商家、监控平台运营。
- **主要功能**：
  - 用户注册与登录
  - 商家搜索与分类浏览
  - 外卖点餐（加入购物车、下单、订单追踪）
  - 到店团购（团购券购买与使用）
  - 用户评价与评分
  - 在线支付（模拟或沙箱集成）
  - 商家后台管理（商品管理、订单处理）
  - 管理后台（商家审核、用户管理）
- **处理流程简要说明**：用户浏览商家和商品 → 选择商品加入购物车 → 提交订单 → 选择支付方式并支付 → 商家接单/核销 → 用户确认收货/使用 → 用户评价。
- **外部接口**：与支付服务接口（模拟支付宝/微信支付）、地图服务接口（高德地图JS API）进行数据交互。本系统为独立产品，不依赖于其他系统。

#### 3.2.2 运行环境

- **硬件环境**：服务器为2核4GB云服务器或同等配置本地环境；客户端为可运行现代浏览器（Chrome、Edge、Firefox）的PC设备。
- **支持环境**：
  - 操作系统：Linux（服务器端），不限（客户端）
  - 数据库：MySQL 8.0
  - 缓存：Redis 6.x
  - 后端运行环境：JDK 11+
  - 前端运行环境：Nginx或其他Web服务器
  - 服务注册与配置：Nacos 2.x

#### 3.2.3 用户的特点

系统用户包括三类角色：

| 用户角色   | 特点                                               | 主要使用场景                             |
| ---------- | -------------------------------------------------- | ---------------------------------------- |
| 普通消费者 | 具有基本Web操作能力，关注易用性和响应速度          | 浏览商家、搜索商品、下单、支付、评价     |
| 商家       | 具有基本电脑操作能力，需要管理店铺信息、商品和订单 | 管理商品上下架、处理外卖订单、核销团购券 |
| 平台管理员 | 具有一定的技术能力，负责平台整体运营管理           | 审核商家入驻、管理用户账号、监控平台数据 |

#### 3.2.4 关键点

- **关键功能**：订单全生命周期管理（从下单到完成）、搜索与筛选、支付处理。
- **关键接口**：支付服务接口、地图展示接口。
- **关键技术**：前后端分离通信、微服务间调用、数据库事务处理。

#### 3.2.5 约束条件

- **开发期限**：第八周至第十五周。
- **人力资源**：5人学生团队。
- **技术栈约束**：后端使用Java/Spring Boot/Spring Cloud，前端使用Vue.js 3，数据库使用MySQL、Redis，不使用Elasticsearch。
- **经费限制**：云服务器费用控制在100元以内。
- **其他约束**：支付功能采用模拟方式实现，不接入真实支付接口；地图服务使用高德地图JavaScript API免费版。

### 3.3 需求规格

#### 3.3.1 软件系统总体功能/对象结构

系统整体采用前后端分离架构，前端Vue.js应用通过HTTP请求调用后端RESTful API。后端微服务体系按业务领域拆分为以下服务模块：

- **用户服务**：处理用户注册、登录、个人信息管理
- **商家服务**：处理商家信息管理、商家入驻审核
- **商品/团购服务**：处理商品管理、分类、上下架
- **订单服务**：处理外卖订单和团购订单全生命周期
- **支付服务**：处理支付请求（模拟）
- **评价服务**：处理用户评价与评分
- **搜索服务**：处理商家和商品的搜索功能
- **API网关**：统一入口，路由转发，认证校验

                |                         |                         |

### 3.4 CSCI能力需求

- ### 3.4 CSCI能力需求

  #### 3.4.1 用户子系统

  ##### 3.4.1.1 用户注册/登录模块（LA-USER-001）

  **需求描述**：系统必须提供高可用、安全的身份认证机制。支持消费者通过多种方式完成注册、登录及登出，同时为平台方提供账号风控管理的基础支撑。

  **输入**：
  - **注册方式（账密）**：用户名（2-20字符）、手机号（11位）、密码（6-20字符，需包含字母和数字）。
  - **登录方式（账密）**：用户名/手机号、密码。
  - **安全校验**：图形验证码（防止脚本暴力撞库）。

  **处理流程**：
  1. **前置校验**：前端校验手机号格式、密码复杂度；触发图形验证码通过后，方可提交登录请求。
  2. **注册逻辑**：后端校验用户名和手机号是否已存在；密码使用BCrypt算法加盐哈希入库；为用户生成唯一编号（用户ID）并初始化默认昵称。
  3. **登录与会话**：校验用户名/手机号和密码，通过后生成JWT令牌返回；后续请求需携带JWT令牌进行身份认证；登录状态有效期为24小时；校验通过后，进入用户主界面。
  4. **风控拦截**：登录时检查平台黑名单，若账号被平台冻结，则阻断登录并返回冻结原因。

  **输出**：
  - **注册成功**：提示注册成功，跳转到登录页。
  - **注册失败**：返回具体错误提示（用户名已存在、手机号已注册、手机号格式错误等）。
  - **登录成功**：返回JWT令牌和用户基本信息（用户ID、用户名、角色），跳转至首页。
  - **登录失败**：返回“用户名或密码错误”或账号状态异常提示。

  **性能要求**：注册和登录接口响应时间不超过500ms。

  ---

  ##### 3.4.1.2 首页/商家浏览模块（LA-HOME-001）

  **需求描述**：作为系统的第一流量分发入口，整合平台的运营位（如轮播图、金刚区导航），并根据特定算法向用户展示综合推荐的商家列表。

  **输入**：
  - **系统级输入**：用户当前定位坐标（经纬度，若拒绝授权则使用默认城市中心点）。
  - **用户交互输入**：分页页码、下拉刷新动作。

  **处理流程**：
  1. **运营位加载**：并发请求后端获取首页轮播图配置和核心业务导航入口（如“外卖专区”、“到店团购”、“周边游玩”）。
  2. **列表推荐算法**：加权排序综合考虑商家评分、月销量、距离、平台广告权重。
  3. **状态标识**：判断商家当前的营业状态，将“休息中”的商家置灰并排在列表末尾。

  **输出**：
  - 渲染包含多模块的首页视图。
  - 商家卡片展示：商家名称、综合评分（带星星图标）、月销量、距离、起送价/配送费（针对外卖）。

  ---

  ##### 3.4.1.3 商家详情/商品浏览模块（LA-MERCHANT-001）

  **需求描述**：用户进入特定店铺后，查看商家的详细资质与信息，并能分类浏览外卖商品或到店团购套餐，是达成交易的关键转化页面。

  **输入**：
  - 商家ID。
  - 切换的商品分类（如“热销”、“主食”、“饮料”）。

  **处理流程**：
  1. **商家信息聚合**：查询商家表，加载顶部店铺信息、公告、详细地址，以及用户对该商家的评价概览（综合评分、评价数量）。
  2. **商品列表加载**：采用双联动滚动列表（左侧分类导航，右侧商品列表）。
  3. **库存与状态实时性**：在加载商品时，过滤掉“已下架”商品；对于库存为0的商品，展示为“已售罄”并禁用添加操作。

  **输出**：
  - 商家顶部信息面板（商家名称、地址、营业时间、联系电话、综合评分）。
  - 结构化的商品列表（分类 → 商品集合）。单品展示：商品名称、描述、价格、月销量。

  ---

  ##### 3.4.1.4 购物车模块（LA-CART-001）

  **需求描述**：作为外卖业务的核心暂存区，用户可将多个外卖商品加入购物车。购物车需按商家进行隔离，并实时计算金额，处理复杂的校验逻辑。

  **输入**：
  - 操作类型：添加商品（商品ID、数量）、修改数量（购物车项ID、新数量）、删除商品（购物车项ID）、清空购物车。
  - 目标商品ID及所属商家ID。

  **处理流程**：
  1. **数据存储**：购物车属高频读写数据，采用数据库存储（购物车表）。
  2. **业务校验**：
     - *库存校验*：每次添加或增加数量，必须校验数据库中的商品剩余库存，超库存则提示并阻断。
     - *价格时效*：购物车中展示的价格应以商品实时价格为准。若商家在用户加购后修改了价格，购物车需以最新价格计算，并在进入结算页时给予变价提示。
  3. **金额计算**：动态计算当前商家购物车内：`总金额 = ∑(商品现价 × 数量)`。
  4. **门槛校验**：对比总金额与商家的“起送价”，前端按钮呈现两种状态：“差 X 元起送”（置灰不可点击）或“去结算”（高亮可点击）。

  **输出**：
  - 购物车列表：商品名称、单价、数量、小计金额、总金额。
  - 满足起送价后的“去结算”按钮。
  - 购物车为空时显示“购物车空空如也”。

  **约束**：购物车仅支持外卖商品，团购商品直接下单不经过购物车。

  ---

  ##### 3.4.1.5 订单管理模块（LA-ORDER-001）

  **需求描述**：系统交易的核心枢纽。负责外卖与团购两种业务形态的订单生成、状态机流转、超时取消以及历史订单查询。

  **输入**：
  - **下单操作**：购物车选中的商品数据/团购商品ID、购买数量、收货地址ID、买家备注（可选）。
  - **状态流转操作**：用户（去支付、取消订单、确认收货/使用团购券）；系统（自动超时取消）。

  **处理流程**：
  1. **订单生成与防超卖**：
     - 接收下单请求后，开启数据库事务。校验商品最新库存。
     - 采用“下单减库存”策略，下单成功即扣减对应商品的库存。
     - 核算最终支付金额：`商品总额 + 配送费/打包费 - 优惠券抵扣 = 实际支付金额`。
     - 生成全局唯一的订单编号，订单状态置为“待支付”。
  2. **状态机流转**：
     - **外卖订单**：待支付 → 待接单 → 配送中 → 已完成。
     - **团购订单**：待支付 → 待使用（生成6位核销码）→ 已完成。
  3. **异常与超时处理**：
     - 订单生成后触发15分钟倒计时。若超时未支付，系统自动将订单状态置为“已取消”，并回滚商品库存。
     - 用户在“待支付”和“待接单”状态可取消订单，取消后恢复库存。
     - 商家若拒单，订单状态变更为“已取消”，触发库存回滚。

  **输出**：
  - 结构化的订单详情页（包含订单编号、商品清单、费用明细、订单状态、核销码（团购）、下单时间）。
  - 支持按状态（全部、待支付、待接单/待使用、已完成/已取消）过滤的历史订单列表。

  **约束**：订单金额低于商家设置的“起送价”时不允许下单。

  ---

  ##### 3.4.1.6 显示配送情况模块（LA-DELIVERY-001）

  **需求描述**：针对处于“配送中”状态的外卖订单，向用户提供实时的配送进度可视化追踪，缓解用户等待焦虑。

  **输入**：
  - 当前处于“配送中”的外卖订单ID。

  **处理流程**：
  1. **骑手信息关联**：当订单被骑手接单后，系统关联接单骑手信息（骑手姓名、电话）。
  2. **地图集成与轨迹展示**：
     - 前端调用高德地图JavaScript API，初始化地图实例。
     - 在地图上标记三个关键节点：商家位置（起点）、用户收货地址（终点）、骑手当前位置（动态点）。
     - 调用高德路径规划接口，绘制出骑手到用户的导航路线。
  3. **动态位置更新**：
     - 前端通过轮询方式获取骑手当前坐标。
     - 根据剩余距离，推算并实时更新预计送达时间。

  **输出**：
  - 嵌入订单详情页的地图交互面板，支持缩放、平移。
  - 醒目的状态提示语（如“骑手距您约1.2km”）。

  ##### 3.4.1.8 优惠券模块（LA-COUPON-001）

  1. **领券逻辑与并发控制**：

  ##### 3.4.2.1 商家注册/登录模块（LA-MERCHANT-002）

  **需求描述**：系统必须提供面向商家的注册与身份认证机制。商家通过注册提交入驻申请，经管理员审核通过后方可登录使用商家后台功能。

  **输入**：
  - **注册信息**：商家名称（2-20字符）、用户名（2-20字符）、密码（6-20字符，需包含字母和数字）、手机号（11位）、商家类型（餐饮/休闲娱乐/生活服务）。
  - **登录信息**：用户名、密码。

  **处理流程**：
  1. **前置校验**：前端校验用户名长度、密码复杂度、手机号格式。
  2. **注册逻辑**：后端校验用户名和手机号是否已注册；密码使用BCrypt算法加密入库；为商家生成唯一编号（商家ID）；商家注册后状态默认为“待审核”。
  3. **登录与会话**：商家输入用户名和密码，后端校验通过后生成JWT令牌并返回；后续请求需携带令牌访问商家端接口。
  4. **状态校验**：登录时检查商家账号状态，若为“待审核”，提示“账号审核中”；若为“已冻结”，提示“账号已被冻结”；仅“营业中”状态可正常登录进入商家后台。

  **输出**：
  - **注册成功**：提示“注册成功，请等待管理员审核”。
  - **注册失败**：返回具体错误提示（用户名已存在、手机号已注册、手机号格式错误等）。
  - **登录成功**：返回JWT令牌及商家基本信息（商家ID、商家名称、状态），进入商家后台主界面。
  - **登录失败**：返回“用户名或密码错误”或状态异常提示。

  **性能要求**：登录接口响应时间不超过500ms。

  ##### 3.4.2.2 商家信息中心管理（LA-MERCHANT-003）

  **需求描述**：系统支持商家对入驻资料与店铺基础信息进行自主修改，包含商家信息查看、资料编辑、店铺简介修改、密码修改等功能，保障商家资料可动态更新、信息安全可控。

  **输入**：
  - **信息查看**：无需额外入参，基于当前登录商家账号自动加载。
  - **资料编辑**：商家名称、联系电话、营业地址、营业时间。
  - **店铺简介修改**：店铺介绍文案（10–300字符）。
  - **密码修改**：原密码、新密码、确认新密码。

  **处理流程**：
  1. **商家信息查看**：根据当前登录商家账号，查询并展示店铺基础资料、入驻信息、营业配置等内容。
  2. **资料编辑**：对输入的商家名称、联系电话、地址等字段进行非空、格式、长度合法性校验，校验通过后覆盖更新数据库对应商家信息。
  3. **店铺简介修改**：校验文案长度合规性，保存修改后的店铺介绍信息。
  4. **密码修改**：校验原密码正确性，二次校验新密码与确认密码一致性，密码合规校验通过后，采用BCrypt加密覆盖更新商家登录密码。

  **输出**：
  - **信息查看**：展示商家名称、联系电话、营业地址、营业时间、店铺简介等完整资料。
  - **资料编辑成功**：返回修改成功提示，实时展示更新后的商家信息。
  - **资料编辑失败**：返回错误提示（手机号格式错误、内容超长、必填项为空等）。
  - **密码修改成功**：返回修改完成提示，引导重新登录。
  - **密码修改失败**：返回对应提示（原密码错误、两次新密码不一致、密码格式不合法等）。

  **约束**：仅登录后的商家可访问本模块；商家名称、联系电话为必填项，不允许为空。

  ##### 3.4.2.3 商品管理模块（LA-MERCHANT-004）

  **需求描述**：系统必须提供商家对商品的管理功能，包括添加商品、下架商品和编辑商品信息，支持选择不同的操作类型进行管理。

  **输入**：
  - **添加商品**：商品名称（2-20字符）、商品描述（5-200字符）、商品价格、库存、商品类型（外卖/团购）、商品分类、图片URL。
  - **下架商品**：商品ID。
  - **编辑商品**：商品ID、商品名称、商品描述、商品价格、库存、商品分类、图片URL。

  **处理流程**：
  1. 根据选择的操作类型（添加/下架/编辑），跳转到对应功能处理流程。
  2. 对输入的商品信息进行合法性校验，包括字段长度、格式、非空判断。
  3. 添加商品时，系统自动生成商品ID，创建商品并保存至数据库，商品状态默认为“在售”。
  4. 下架商品时，根据商品ID匹配目标商品，校验该商品属于当前商家后执行下架操作，更新商品状态为“已下架”。

  **输出**：
  - **添加商品成功**：返回成功提示，显示新增商品的基本信息。
  - **添加商品失败**：返回具体错误提示（字段长度不合法、信息不完整等）。
  - **下架商品成功**：返回成功提示，更新商品状态为已下架，用户端不可见。
  - **下架商品失败**：返回具体错误提示（商品不存在、无操作权限等）。
  - **编辑商品成功**：返回成功提示，显示更新后的商品信息。
  - **编辑商品失败**：返回具体错误提示（商品不存在、输入信息不合法等）。

  **性能要求**：接口响应时间不超过500ms。

  **约束**：商家只能管理自己店铺的商品；已下架商品不可被用户购买；商品价格变更需实时同步至购物车。

  #### 3.4.3 骑手后台子系统

  ##### 3.4.3.1 登录注册模块（LA-RIDER-001）

  **需求描述**：系统必须提供面向骑手的注册与身份认证机制。骑手需通过平台审核后方可登录接单，确保配送人员的身份可靠性和服务规范性。

  **输入**：
  - **注册信息**：姓名、手机号（11位）、身份证号、密码（6-20字符，需包含字母和数字）。
  - **登录信息**：手机号、密码。
  - **安全校验**：图形验证码。

  **处理流程**：
  1. **前置校验**：前端校验手机号格式、密码复杂度、身份证号格式（18位）。
  2. **注册逻辑**：后端校验手机号是否已注册；密码使用BCrypt算法加密入库；骑手注册后状态默认为“待审核”；为骑手生成唯一编号（骑手ID）。
  3. **登录与会话**：骑手输入手机号和密码，后端校验通过后生成JWT令牌并返回；后续请求须携带令牌访问骑手端接口。
  4. **状态校验**：登录时检查骑手账号状态，若为“待审核”，提示“账号审核中”；若为“已冻结”，提示“账号已被冻结，请联系管理员”；仅“已通过”状态可正常登录。
  5. **审核流程**：管理员在后台审核骑手的身份证信息，审核通过后骑手状态变更为“已通过”；审核拒绝需填写拒绝原因。

  **输出**：
  - **注册成功**：提示“注册成功，请等待审核”。
  - **注册失败**：返回具体错误提示（手机号已注册、身份证格式错误等）。
  - **登录成功**：返回JWT令牌及骑手基本信息（骑手ID、姓名、状态），进入骑手主界面。
  - **登录失败**：返回“手机号或密码错误”或状态异常提示。

  **性能要求**：登录接口响应时间不超过500ms。

  ##### 3.4.3.2 接单模块（LA-RIDER-002）

  **需求描述**：骑手登录后可查看待配送的外卖订单池，选择接单并进行配送状态流转，支持配送全生命周期的管理。

  **输入**：
  - **接单操作**：订单ID。
  - **配送状态变更**：订单ID、操作类型（取餐完成/送达确认）。
  - **拒单操作**：订单ID、拒单原因（可选）。

  **处理流程**：
  1. **订单池展示**：骑手进入接单页，系统展示当前状态为“待接单”的外卖订单列表。每条订单显示：订单ID、商家名称、取餐地址、送达地址、配送距离、预计配送费、下单时间。
  2. **接单**：骑手点击“接单”，系统校验订单是否已被其他骑手接单；若未被抢单，则将该订单状态更新为“配送中”，并关联骑手ID；若已被抢单，提示“订单已被其他骑手接取”。
  3. **配送状态流转**：
     - **取餐完成**：骑手到达商家后点击“确认取餐”，订单状态保持“配送中”。
     - **送达确认**：骑手到达用户处点击“确认送达”，订单状态变更为“已完成”，配送费计入骑手当日收入。
  4. **拒单**：骑手接单后规定时间内可拒单；拒单后订单重新进入订单池，清除关联的骑手ID；拒单原因可选（距离过远、配送时间冲突、其他），拒单记录留存。
  5. **配送超时提醒**：若订单超过预计配送时间未完成送达，系统向骑手推送超时提醒（前端轮询）；超时订单在骑手列表中标红显示。

  **输出**：
  - **订单池列表**：实时刷新，按距离和配送费排序。
  - **接单成功**：订单卡片高亮显示，进入“我的配送”列表。
  - **接单失败**：提示已被抢单，刷新订单池。
  - **状态更新**：配送状态实时同步至后端，用户端可查看状态变化。
  - **配送完成**：配送费累计更新，订单从“进行中”移至“已完成”。

  **性能要求**：
  - 订单池刷新频率：建议30秒轮询一次。
  - 接单接口需保证并发安全，防止同单被多骑手接取。

  **约束**：
  - 每位骑手同时接单上限为3单。
  - 骑手仅可接取距离当前位置15公里以内的订单。

  ##### 3.4.3.4 钱包模块（LA-RIDER-004）

  **需求描述**：骑手需具备钱包功能，可查看配送收入明细和累计余额，支持简单的提现申请操作。

  **输入**：
  - **提现申请**：提现金额、收款方式（模拟，如银行卡号后四位）。
  - **查询请求**：时间范围筛选（可选）。

  **处理流程**：
  1. **收入明细**：骑手进入钱包页，查看当日、本周、本月的收入明细列表。每条记录包含：订单ID、完成时间、配送费金额。
  2. **余额计算**：系统实时计算骑手累计可提现金额（已完成配送费总和 - 已提现金额）。
  3. **提现申请**：骑手输入提现金额（不超过可提现余额），提交提现申请；系统生成提现记录，状态为“处理中”；扣减可提现余额。
  4. **提现审核**：管理员在后台查看提现记录，操作“确认打款”或“拒绝”（课程项目中可简化：提现申请提交后直接置为“已打款”模拟自动处理）。

  **输出**：
  - **钱包余额**：可提现金额、累计收入金额。
  - **收入明细列表**：按时间倒序展示。
  - **提现记录**：提现金额、申请时间、状态。
  - **提现成功/失败提示**。

  **约束**：
  - 提现金额需为整数元。
  - 每日提现次数上限为1次。

  ##### 3.4.3.5 会话模块（LA-RIDER-005）

  **需求描述**：骑手在配送过程中可通过临时会话功能与下单用户或供餐商家进行即时沟通，解决配送中遇到的问题。

  **输入**：
  - **发送消息**：订单ID、消息内容（文字，0-200字）、接收方类型（用户/商家）。
  - **查看消息**：订单ID。

  **处理流程**：
  1. **会话入口**：骑手在订单详情页点击“联系用户”或“联系商家”，进入该订单的临时会话窗口。
  2. **会话创建**：系统根据订单ID和参与方（骑手-用户 或 骑手-商家）生成唯一会话标识。若会话已存在，则加载历史消息。
  3. **消息收发**：骑手发送消息，后端存储消息记录（发送方ID、接收方ID、订单ID、内容、时间戳），前端通过轮询方式获取新消息（建议10秒轮询）。
  4. **会话有效性**：会话与订单生命周期绑定，订单完成后会话变为只读（不可再发送新消息），订单完成24小时后会话关闭。
  5. **会话列表**：骑手可查看最近会话列表，按最后消息时间排序。

  **输出**：
  - **会话窗口**：显示消息记录，区分己方和对方消息气泡。
  - **新消息提示**：未读消息以红点或数字角标提示。
  - **消息发送成功/失败状态**。

  **性能要求**：消息轮询频率不超过10秒一次以减轻服务器压力。

  **约束**：
  - 会话仅支持文字消息，不支持图片和文件。
  - 会话内容不可修改和撤回（简化实现）。
  - 会话不采用WebSocket实时通信，使用HTTP轮询方式模拟实时效果。
  - 会话数据存储在MySQL中，不引入独立IM中间件。

### 3.5 CSCI外部接口需求

#### 3.5.1 接口标识和接口图

本系统的外部接口包括：

| 接口标识   | 接口名称     | 接口实体                 | 说明         |
| ---------- | ------------ | ------------------------ | ------------ |
| IF-PAY-001 | 支付服务接口 | 模拟支付服务（内部服务） | 模拟支付处理 |
| IF-MAP-001 | 地图展示接口 | 高德地图JavaScript API   | 商家位置展示 |

接口关系图：

```
[生活助手平台] ---HTTP---> [模拟支付服务（内部）]
[生活助手平台前端] ---JS API---> [高德地图服务（外部）]
```

#### 3.5.2 支付服务接口（IF-PAY-001）

**接口类型**：RESTful API（内部微服务调用）

**所需的数据元素特性**：

| 数据元素      | 类型       | 说明                      |
| ------------- | ---------- | ------------------------- |
| orderId       | String     | 订单ID，唯一标识          |
| userId        | Long       | 用户ID                    |
| amount        | BigDecimal | 支付金额，精确到分        |
| payMethod     | String     | 支付方式（ALIPAY/WECHAT） |
| transactionId | String     | 支付流水号（系统生成）    |
| status        | String     | 支付状态（SUCCESS/FAIL）  |
| timestamp     | DateTime   | 支付时间                  |

**通信方法特性**：

- 通信方式：HTTP POST请求
- 请求格式：JSON
- 响应格式：JSON
- 超时时间：5秒

**协议特性**：
- 请求需携带JWT令牌进行身份认证（通过API网关转发）
- 支付失败时返回错误码和错误消息

**模拟支付处理逻辑**：
1. 接收支付请求，验证参数完整性。
2. 若订单状态为“待支付”且金额匹配，90%概率模拟支付成功。
3. 若模拟支付失败（10%概率），返回“支付失败，请重试”。
4. 支付成功后生成UUID格式的流水号。

#### 3.5.3 地图展示接口（IF-MAP-001）

**接口类型**：JavaScript API（高德地图）

**用途**：在商家详情页展示商家地理位置。

**调用方式**：前端通过高德地图JS API 2.0加载地图组件，传入商家经纬度坐标显示标记点。

**所需数据**：商家经度（longitude）、纬度（latitude）、商家名称。

**约束**：使用高德地图免费版，需申请API Key。经纬度数据在商家入驻时预设（模拟数据）。

### 3.18 算法说明

本系统业务逻辑不涉及复杂算法，主要处理为常规的增删查改操作。以下列出需注意的处理公式：

- **商家综合评分计算**：`商家评分 = SUM(该商家所有评价的评分) / 评价数量`，保留1位小数。
- **订单总金额计算**：`订单总金额 = SUM(订单明细中 单价 × 数量)`。
- **购物车总金额计算**：同订单总金额计算逻辑。
- **团购券核销码生成**：6位大写字母数字随机组合，需保证同一商家下的券码唯一。
