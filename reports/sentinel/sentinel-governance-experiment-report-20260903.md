# Sentinel 流量治理实验报告

## 1. 实验概述

本实验用于验证 Life Service 微服务系统在引入 Sentinel 后的基础流量治理能力，重点覆盖网关入口限流、业务服务限流、内部依赖限流以及依赖服务不可用时的业务降级。实验于 2026-09-03 在云服务器 K3s 集群环境执行，探测流量从云服务器直接访问公网 Gateway 地址 `http://47.120.37.61:30081`，Sentinel 规则通过 Nacos 配置中心读取，Nacos 访问地址为云服务器本机端口转发后的 `http://127.0.0.1:8848`。

实验规则使用 Nacos `DEFAULT_GROUP`，未使用 namespace，报告中的 Nacos namespace 记为 `public`。实验过程中通过脚本临时下调部分 Sentinel 规则阈值，脚本在对应场景结束后自动恢复原始 Nacos 规则。

## 4. Sentinel 规则覆盖范围

当前项目已经为 Gateway 和各业务服务准备了 Nacos Sentinel 规则文件，主要包括：

| 类型 | 配置文件示例 | 覆盖内容 |
| --- | --- | --- |
| Gateway API 分组 | `configs/nacos/sentinel-api-gateway-gw-api-group.json` | 将认证、搜索、推荐、订单、支付、用户、商家、骑手、互动、管理等入口路径归入 API 分组 |

## 5. 实验步骤与结果

### 5.1 S0 基线探测

实验命令使用 `--mode baseline`，不发布临时 Sentinel 规则。探测目标为 `GET /api/captcha` 和 `GET /api/search?keyword=Braised`。

| 指标 | 数值 |
| --- | ---: |
| 总请求数 | 24 |
| HTTP 429 | 0 |
| 业务 429 | 0 |
| HTTP 503 | 0 |
| 业务 503 | 0 |
| 降级响应数 | 0 |
| 平均延迟 | 169.66 ms |
| 最小延迟 | 17.23 ms |
| P95 延迟 | 660.38 ms |
| 最大延迟 | 729.16 ms |

结论：基线阶段所有探测均返回 HTTP `200` 和业务 `code=200`，说明 Gateway、公网 NodePort、验证码接口、搜索接口以及后端基础链路在实验开始时处于可用状态。

### 5.2 S1 Gateway 入口限流

实验命令使用 `--mode gateway-flow --apply-temporary-rules`。脚本将 `sentinel-api-gateway-gw-flow.json` 中 `gateway-search-api` 的阈值临时下调为 `count=1`，然后连续探测搜索入口。

| 指标 | 数值 |
| --- | ---: |
| 总请求数 | 12 |
| HTTP 429 | 3 |
| 业务 429 | 3 |
| HTTP 503 | 0 |
| 业务 503 | 0 |
| 平均延迟 | 60.38 ms |
| 最小延迟 | 4.34 ms |
| P95 延迟 | 193.40 ms |
| 最大延迟 | 193.40 ms |

典型响应消息为“系统繁忙，请稍后重试”。

结论：Gateway 入口限流生效。被 Sentinel 拦截的请求在网关层返回 HTTP `429` 和业务 `code=429`，未继续压入下游业务服务，达到了入口削峰和保护后端的目的。

### 5.3 S2 业务服务限流

实验命令使用 `--mode service-flow --apply-temporary-rules`。脚本将 Gateway 搜索分组阈值临时调高，避免网关提前拦截，同时将商家服务 `/api/search` 的流控阈值临时下调为 `count=1`。

| 指标 | 数值 |
| --- | ---: |
| 总请求数 | 12 |
| HTTP 429 | 2 |
| 业务 429 | 2 |
| HTTP 503 | 0 |
| 业务 503 | 0 |
| 平均延迟 | 320.66 ms |
| 最小延迟 | 24.12 ms |
| P95 延迟 | 3392.07 ms |
| 最大延迟 | 3392.07 ms |

典型响应消息为“请求过于频繁，请稍后重试”。首个成功请求延迟为 3392.07 ms，是该场景平均值偏高的主要原因，后续成功或限流响应多数在几十毫秒级。

结论：业务服务级 Sentinel 流控生效。与 S1 不同，本场景由商家服务自身规则触发，响应消息来自业务服务统一 Sentinel Block 处理逻辑，说明网关放行后，服务自身仍具备第二层保护能力。

### 5.4 S3 内部依赖保护

实验命令使用 `--mode dependency-fallback --apply-temporary-rules`。脚本将 Gateway 商家看板入口和商家服务看板接口阈值调高，同时将订单服务内部接口 `/internal/orders/merchant-dashboard` 阈值临时下调为 `count=1`，通过商家看板间接压测订单服务内部接口。

| 指标 | 数值 |
| --- | ---: |
| 总请求数 | 13 |
| 登录请求数 | 1 |
| 看板请求数 | 12 |
| HTTP 429 | 0 |
| 业务 429 | 4 |
| HTTP 503 | 0 |
| 业务 503 | 0 |
| 降级响应数 | 0 |
| 平均延迟 | 1211.49 ms |
| 最小延迟 | 20.87 ms |
| P95 延迟 | 4604.28 ms |
| 最大延迟 | 4604.28 ms |

典型业务错误为“依赖服务请求过多，请稍后重试”。材料中的 `protected-service.log` 显示商家服务调用订单服务内部接口时收到 `status=429`，随后全局异常处理返回业务 `code=429`。

结论：订单服务内部接口的 Sentinel 限流保护已经生效，但商家看板没有在依赖返回 `429` 时进入降级数据路径。本场景应判定为“内部依赖限流有效，业务降级未覆盖依赖限流错误”。这与当前代码策略一致：`MerchantDashboardService` 只对 `503` 或 `5xx` 类依赖错误返回降级看板，对 `429` 仍按业务异常透传。

S1、S2、S3 的临时规则执行完毕后，脚本恢复原始 Nacos 规则。随后再次使用 `--mode baseline --iterations 5` 进行恢复复查。

| 总请求数 | 10 |
| HTTP 429 | 0 |
| 业务 429 | 0 |
| HTTP 503 | 0 |
| 业务 503 | 0 |
| 降级响应数 | 0 |
| 平均延迟 | 136.91 ms |
| 最大延迟 | 691.87 ms |

结论：临时 Sentinel 规则已恢复，基线接口不再持续出现 `429`，说明实验脚本的备份和恢复机制有效。

### 5.6 S4 依赖服务故障降级

S4 不使用临时 Sentinel 低阈值规则，而是通过故障注入脚本将 `order-service` 缩容到 0，使商家看板依赖的订单服务真实不可用。随后运行 `--mode dependency-fallback` 探测商家看板。

| 指标 | 数值 |
| --- | ---: |
| 总请求数 | 11 |
| 登录请求数 | 1 |
| 看板请求数 | 10 |
| HTTP 429 | 0 |
| 业务 429 | 0 |
| HTTP 503 | 0 |
| 业务 503 | 0 |
| 降级响应数 | 10 |
| 平均延迟 | 265.00 ms |
| 最小延迟 | 17.23 ms |
| P95 延迟 | 2665.38 ms |
| 最大延迟 | 2665.38 ms |

故障期 10 次商家看板探测全部返回 HTTP `200`、业务 `code=200`，并携带 `data.degraded=true`、`data.degradedDependency=order-service`、`fallbackReason=remote code 503`。典型降级消息为“订单服务暂不可用，已返回临时看板数据，请稍后刷新。”

结论：当订单服务没有可用实例时，商家看板能够返回稳定的临时看板数据，不向前端暴露 500 或连接错误，依赖不可用类故障降级通过。

## 6. 综合判定

| 场景 | 目标 | 结果 | 判定 |
| --- | --- | --- | --- |
| S0 基线 | 正常链路可用，无误限流 | 所有请求 HTTP 200 / code 200 | 通过 |
| S1 Gateway 入口限流 | 网关层拦截热点入口流量 | 12 次中 3 次返回 429 | 通过 |
| S2 业务服务限流 | 服务层独立限流 | 12 次中 2 次返回 429 | 通过 |
| S3 内部依赖保护 | 内部接口限流并验证依赖保护 | 订单内部接口触发 429，商家看板透传业务 429 | 部分通过 |
| S0 恢复复查 | 临时规则恢复后正常访问 | 无 429/503 | 通过 |
| S4 依赖故障降级 | 依赖服务不可用时看板降级 | 10 次看板请求全部 degraded=true | 通过 |

总体结论：当前 Sentinel 引入已经覆盖入口限流、服务级限流和依赖不可用降级等关键能力。系统能够在网关层和业务服务层主动拒绝超阈值流量，也能在订单服务真实不可用时为商家看板返回可解释的降级数据。需要注意的是，依赖服务被 Sentinel 限流时返回的 `429` 当前没有被商家看板转换为降级数据，而是透传为业务错误；如果产品目标是“商家看板尽量始终可读”，这一点需要继续完善。

## 7. 问题分析

### 7.1 S3 未返回降级数据

S3 中订单服务内部接口 `/internal/orders/merchant-dashboard` 触发 Sentinel 限流后，商家服务收到依赖返回的 `429`。当前 `FeignGovernanceConfig` 会将 HTTP `429` 转换为业务码 `429`，消息为“依赖服务请求过多，请稍后重试”；`MerchantDashboardService` 对 `429` 的处理是抛出业务异常，而不是返回降级看板。因此 S3 的表现是“依赖保护成功，调用方体验未降级”。

该行为不一定是错误，取决于业务策略：

- 如果 `429` 被视为短时过载，应保留 429，让前端或调用方稍后重试。
- 如果商家看板属于高可用展示型页面，应将 `429` 也纳入降级条件，返回带 `degraded=true` 的临时看板。

### 7.2 业务降级覆盖仍偏聚焦

本次实验证明商家看板对订单服务不可用有降级能力，但并未证明所有跨服务链路均已有业务兜底。例如订单创建依赖商家商品、支付状态更新依赖订单、履约任务依赖订单等链路是否需要降级、失败快返或补偿，需要按业务重要性继续拆分验证。

### 7.3 Sentinel Dashboard 未部署

当前规则由 Nacos JSON 文件和 CI/CD 发布管理，实验可通过脚本完成，但缺少 Sentinel Dashboard 后，无法在页面上实时查看资源名、通过量、拒绝数和熔断状态。对课程实验或小规模部署影响不大；对线上运维、调参和排障来说，可观测性仍不够直观。

## 8. 优化建议

1. 明确 `429` 的调用方策略。对商家看板这类展示型接口，建议将依赖 `429` 也转为降级看板；对下单、支付、库存扣减等强一致操作，建议继续返回明确失败，避免用户误以为操作成功。
2. 补充 S3 的期望定义。如果目标是验证“内部依赖限流”，当前结果已经通过；如果目标是验证“内部依赖限流时调用方降级”，则需要修改业务代码或调整实验判定。
3. 继续扩展跨服务链路实验。建议优先覆盖订单创建、支付回调、骑手接单、用户订单列表、商家订单列表等高频链路。
4. 为 Sentinel 规则增加版本化说明。每次修改 Nacos 规则文件时，在报告或变更说明中记录规则资源名、原阈值、临时阈值和恢复方式。
5. 评估是否部署 Sentinel Dashboard。若后续需要演示实时流控效果或长期运维，Dashboard 能显著降低观察成本；若只是 CI/CD 管理规则和脚本化实验，Nacos 加报告文件已经可以支撑基础复现。

## 9. 结论

本次 Sentinel 实验总体通过。系统在正常情况下可稳定访问；Gateway 入口限流和业务服务限流均能产生符合预期的 `429` 响应；临时规则恢复后系统回到正常状态；当订单服务真实不可用时，商家看板能够返回 `degraded=true` 的临时数据，避免故障扩散到前端页面。

实验同时暴露出一个治理边界：依赖接口被 Sentinel 限流返回 `429` 时，商家看板当前不会降级，而是透传“依赖服务请求过多”。后续应根据业务目标决定是否将该类错误纳入降级范围。
